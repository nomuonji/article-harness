# Editorial Quality — 記事を増やす前に価値を作る
Version 1.0.0 / 2026-10-20

## Mission / scope
**Site Operatorの管理有無にかかわらず、サイト立ち上げ前・最初の記事・通常の執筆/更新・SEO改修・既存記事の監査に適用する。** 新しいサイトがSEO運用へ引き渡される前に生じる「記事を一定数埋めるための量産」を防止する。言い換えや字数ではなく、読者にとっての検証可能な価値を審査する。

本Skillは**編集判断の作業契約**であり、スクリプトの実行権、GitHubの必須チェック、CMSの公開制御、Googleインデックスを自動的に実現しない。実装・公開・ステータス・実測の正本は各サイトのGitHub/CMSと担当Operator。My Portal chatSkills DBが本Skill本文の正本で、スクリプト・独立DB・新サービスはこのSkillに含めない。必要なら**各プロジェクト側**で検査スクリプトを実装し、本Skillに従うエージェントが実行する。使えない検査は未実行と記録する。スクリプト検査が合格しても意味的な編集品質は保証されない。

他の規則との関係：各サイト固有の編集憲章・ブランド方針、著作権・広告表記・プライバシー・法令、GitHub/CI/既存CMS publish gate/Agent HQ Methodは必ず尊重する。本Skillを理由に既存の安全・公開制御を迂回しない。サイト固有の表現は一律の構成・文体に押し込めない。既存の `public-content-publishing` はCMS/privacy/公開手順、`seo-article-evidence-training` はブラインドSEO評価・公開後実測、`human-web-voice` は媒体らしい語り口、`natural-japanese-editor` は意味を変えない推敲を担当。本Skillはその**前段と横断の編集可否判定**を担当する。

## Trigger
- 新規サイト/ブログ/メディアを企画・立ち上げ・量産初期データを投入する
- サイトをまだSites Operatorに登録していない状態で記事を書き始める
- 新規記事・比較/ランキング・FAQ/DB解説・人物プロフィールを企画/作成する
- 記事をリライト/改稿/翻訳する、SEO記事を増やす
- 既存サイト全体を監査し、公開継続/修正/統合/停止を検討する
- 公開前またはPR/デプロイ前に記事品質を審査する
- 「品質」「独自価値」「検索に評価されない」「記事が薄い」への対策を求められた場合

プロジェクト固有の仕事ではMy Portal `world_map_get` →該当サイトのrepo/方針を確認する。プロジェクト外の一般的な文章執筆に過剰な外部調査やサイト運用を持ち込まない。

## Invariants — 絶対条件
1. **掲載数・公開速度・検索語の消化は目的ではない。** 明確な価値が1記事分しかなければ1記事で止める。初期記事0件やdraft保持も正当な結果。公開基準を下げて件数を埋めない。
2. **URLの存在・出典の件数は主張の裏付けではない。** 重要な数値、法律、料金、順位、契約、人物経歴、受賞歴、場所、日時、入場条件を主張単位で原典と照合する。ソース自身の対象範囲/掲載日/推定/広告性を読む。
3. **分からないことを埋めない。** 不明・出典間不一致・古い情報・確認不能は明示し、必要なら主張を削除する。創作した訪問・実験・インタビュー・購入・一次データ・口コミを使わない。
4. **同じサイトの記事と競合させない。** 新記事の前に同テーマ/同意図の既存記事を確認し、追加価値がないなら既存記事の修正・統合・企画棄却を優先。URL・被リンク・canonicalを無根拠に壊さない。
5. **本文以外も審査する。** title/description, FAQ, comparison table, schema/JSON-LD, alt text, hub/index snippets, recommendations, translated pages, booking/CTA claimも確認する。個別記事を直した場合、集約記事に旧数値が残らないか確かめる。
6. **文章が自然・長文・SEO最適化されているだけでは合格しない。** 形式的な網羅・水増し・AIの型文・名前の入替記事・中身のないランキングは不合格。
7. **例外は透明に。** 検証しきれない主張を別の出典に置換しただけで「検証済み」と宣言しない。評価不能は合格扱いしない。著作権/商標/プライバシー/広告の別途制約を無視しない。

## Phase A — サイト立ち上げゲート（記事本文より先）
サイト管理ツールへの登録有無に関係なく、サイト新設・リブランディング・大量の初期記事導入時に、以下を短い内部編集ブリーフとして確定する。
- **誰の、どんな状況の、具体的な問い**に答える媒体か。誰が読んでも同じ「○○完全ガイド」量産ではないか。
- **サイトが持つ情報上の優位性は何か。** 例：原語の一次資料を英語で解き明かす、資料間の矛盾を整理、実際に収集したデータ、独自の比較手法、特定利用場面の判断ツール、観察・表現の独自性。独自データがない場合も、厳密な二次的分析/編集で価値を作れるが何が新しい理解か特定する。
- 最初の**3–5件の候補**ごとに、想定読者、読後に可能になること、裏付け材料、既存記事との差、公開する理由を示す。3–5件は候補確認の目安であり公開ノルマではない。
- 未調査/弱い/類似した企画は**draft/reject**。初期サイトに「とりあえず20記事」を投入しない。サイトの世界観、ターゲット、記事種別の違いに応じた編集契約を各repoで参照する。

## Phase B — 記事企画ゲート
**本文執筆より前**に最低限以下を決める。
- reader_job: どの読者が何を判断/理解/できるようになるか。
- central_question: タイトルが答える一つの中心的な問い。
- differentiation: 既存自社記事・入手できる主要記事・汎用AI回答にない、**具体的に実演できる**価値を一つ以上。内容/観測した競合本文を読まず「競合にない」と断言しない。検索/SERPが利用できないときは未確認と記録し、虚偽の分析を作らない。
- evidence_plan: 確認すべき重要主張とアクセスできる原典。調べられない主張は使わない。
- article_form: 参照資料、法律解説、人物、比較、旅行実用、観察、批評、ニュース、個人体験、DBページなど用途を決める。型ごとに異なる証拠と読書順序を要求し、全記事に同じ表/FAQ/5見出しを強制しない。
- editorial_promise: 読後の利得を一文で言えない/既存資料を丸めただけなら、執筆せず企画を変更・棄却する。

## Phase C — Source packet & claim ledger（記事制作中）
必要な範囲で原典を読む。出典の件数を稼がない。本文の重要主張について私的な軽量表（別DB不要）を作る。

| claim | source & original passage/data | time/scope | judgment |
| --- | --- | --- | --- |
| 年間ランキング1位 | 同一プラットフォームの元ランキング、年・部門・集計対象 | その対象年とカテゴリのみ | 支持／不支持／一部／不明 |
| 店舗の料金と入場条件 | 店舗の当該日公式イベント料金表 | 日付・客種・条件 | 支持／変更可能／未確認 |
| 法律により合法 | e-Gov等の該当法令条文と行政解説 | 法域・適用条件・改正時点 | 支持／誇張／法的留保 |

証拠の強さは**主張との距離**で決める。本人/メーカー/政府/出版社は自分の発表内容には強いが、ランキング、市場全体、独立した効果測定はその発表だけでは証明できない。広告・プレスリリースは公表の事実と販売成果を区別する。Wikipedia/まとめ/検索スニペットは調査入口には使えるが、高リスクな細部の最終根拠にしない。時間依存情報は日付、更新主体、将来/予定/実績を分ける。閲覧失敗/403/429/非公開は証拠として扱わない。権利・ライセンスもチェックする。

**高リスク領域**（法律、医療、金融、税、行政手続、治安、安全、料金/契約、本人の経歴・プライバシー）では一次/公的資料と適用条件を重点チェック。実用的に必要な留保は本文の適切な場所に置き、免責を積み重ねて不正確な内容を隠さない。

**非事実型**（批評、エッセイ、創作、ユーモア、個人的観察）では「一次資料3件」という機械的ノルマは課さず、実際の題材・観察・選択・洞察・語り手の独自性を吟味する。フィクションと実話をすり替えない。

## Phase D — 独立編集・最終審査（完成した全文に対して）
執筆者と同一の出力を自己正当化しないよう、**別の評価視点/可能なら別エージェント**で批判的審査を行う。利用可能なら元ネタ・重要主張・原典・競合本文・改稿前後と完成版を渡す。独立実行できなければ「独立審査未実施」と報告し、自己採点で代用したと偽らない。

順に読む：
1. **Factual integrity:** material claimがsourceで裏付くか。否定・留保・誇張・因果・集計対象、未来/過去、矛盾、画像出典、引用/翻訳の忠実性。
2. **Substantive value:** 読者が得る新しい具体情報、比較、判断、例、データ、洞察が本当に本文に存在するか。表だけあるが中身が不明なら不合格。
3. **Originality and redundancy:** 競合や自サイト記事の焼き直し・同一テンプレ/固有名詞置換・リライトだけか。実際の閲覧範囲と判断限界を区別。
4. **Reader experience:** 冒頭の約束、本文の認知順序、理解の負荷、冗長・過度な定型、媒体固有の面白さ/声を確認。数字に見えない価値も評価する。
5. **Full-surface consistency:** タイトル、要約、FAQ、集約記事、schema、内部リンク、古い引用、版違い/翻訳、PR/アフィリエイト表示と整合するか。
6. **Sustainability:** 著者の「確認済み」と更新予定の区別、時限データ、権利、出典の保存性、再検証可能な状態か。

**固定の点数を合格条件にしない。** 生成者が都合よく自己採点できるため、まず重大な欠陥を判定し、必要ならサイト固有の定義済み評価軸で補助スコアを出す。文章・出典・見出しの件数を合否の代理指標にしない。

## Decision contract
- **PASS**: 検証範囲と読者価値を具体的に示せ、重大な未検証断定/権利上の懸念やサイト内矛盾がない。既存の技術/公開ゲートも別途満たす必要あり。
- **REVISE**: 価値はあるが、特定可能な未確認事実、読者の不足回答、構成の欠陥がある。修正すべき主張と原典を明示し、改稿**後に全文再審査**。
- **REJECT / MERGE / DRAFT**: 独自価値がない、差別化を作れない、観測できない数値依存の量産、既存記事と重複。統合・保留・企画棄却を検討。価値のために言い換えを量産しない。
- **INSUFFICIENT EVIDENCE**: 利用可能な情報だけでは重要事項を判断できない。合格や改善済みと報告しない。根拠取得不能なら該当主張を取り除き、記事として意味が残るか再判断する。

出力は長い儀式的なチェックリストではなく、**結論、根拠となる具体箇所、残存不明点、修正した実物、公開の可否**を簡潔に報告する。発見事項/不合格理由は既存のPR・issue・サイトrepoの編集記録等へ保存できるなら保存。新しいIdea DB、品質ログサービス、スケジュール、UIを新設しない。

## Phase E — 既存サイト全体の監査
1. 実際のリポジトリ/CMSの公開記事を**全件列挙**し、公開/下書きと更新時点を確認。検索用一覧の断片を全件と取り違えない。
2. 各本文・frontmatter・引用・主張を見て、**重大誤情報/法的問題 → 無根拠な数値/経歴 → 既存記事との重複 → 明確な読者価値不足 → 文章表現**の順で優先づける。サンプリングは「部分監査」と表示。
3. 共通化した記事テンプレやhub/FAQに旧情報が残っていないか追う。単一ページ改稿だけを全サイト改善とみなさない。
4. URLと検索実績を可能なら保全しつつ、個別記事の具体的な改稿・統合・保留を決定。一律noindex/大量削除は自動で行わない。品質不振だけからGoogleが低品質と判定したと断言しない。
5. 修正後はファイルreadback、可能ならビルド・本番HTTP/表示・内部リンク・canonicalを確認。**GitHubマージ≠本番反映≠Google再クロール/インデックス回復**。未確認なら未確認と報告。

## Red-team regression examples — Chonmage EN (2026-10)
これらは**防ぐべき失敗モードの教材**であり、他サイトに成人向けの文体/構成を持ち込むことを意味しない。
- Roppongi club記事: 年月日によって変わる入場料を「必ず¥X」と断定、Azabujuban所在の店舗をRoppongiの所在地として書く → 当日の公式イベント/店舗情報を確認しなければ不合格。
- Love hotel記事: 出典不明の「30,000施設」「年間5億回」「市場40億ドル」を装飾的に入れる → 原典/算出方法がなければ削除。
- 法律記事: 行政上の届出と適法性を混同、「穴を使えば合法」と説明 → 適用法令の条文と射程を照合。
- 人物記事: Wikipedia/1本のX投稿だけでFANZA年間順位、専属契約、非公開な動機まで断定 → 元ランキング/本人・事務所/発表を確保するか断定を削除。一次資料同士の生年の相違は両論を示し、無断確定しない。
- 個別記事の訂正後も「人物総合ガイド」に旧ランキングが残る → **集約ページ、FAQ、構造化データまで横断チェック**。
- 多数の記事を「出典があるイベント表」に差し替えただけで全文品質合格と呼ぶ → 情報が正しくても固有の読者価値が弱ければ要再企画。

## Tool and workflow boundaries
- ChatGPT: 専門正本をMy Portal / 各repo / 必要なOperatorから取得し、現実に使えるツールの範囲で調査・改稿・レビュー。使えないスクリプト/外部APIを実行済みと報告しない。
- Claude Code / Codex: 本文とrepoを読み、プロジェクト内に実在するスクリプトを**必要な場合に**実行できるが、本Skill自体はスクリプト/CLIコマンドを同梱・強制しない。
- GitHub Actions/CMS: 強制的にデプロイを阻止したい場合は**プロジェクト側の実装**（CI required check、CMS approval）を別途整備。skill実行やMy Portal DB保存だけで自動公開阻止を保証しない。
- Sites OperatorはSEO実測/SEO Taskの専門担当であり、**本Skillの適用範囲を限定しない**。未管理サイト、新規サイト、社内ノート、DB説明ページ、ランディング記事にも公開品質判断として適用できる。
- SNSや単なる短文チャットまで詳細な記事監査を機械適用しない。目的と媒体に応じて簡潔な手順で扱う。
